# 固定任务、多种子评估

本阶段评估现有受限抓放链路：任务文字 → 模型生成程序 → AST 校验 → 仿真 → 独立目标检查。它是开发基线，不是论文完整任务集，也不包含分层函数生成、空间推理或实机实验。

## 固定协议

默认清单为 `examples/evaluation/block_to_bowl_v1.json`，在首次调用之前确定以下 15 个试验：

| 任务 | 独立目标 | 场景 seed |
| --- | --- | --- |
| single | 蓝块 → 黄碗 | 0、1、2、3、4 |
| match_colors | 蓝块 → 蓝碗；红块 → 红碗 | 0、1、2、3、4 |
| cross_colors | 蓝块 → 红碗；红块 → 蓝碗 | 0、1、2、3、4 |

按 seed 优先、清单中的任务顺序串行执行。每个试验独立请求一次模型，不跨 seed 复用模型回复，不自动重试、不修改回复、不用手写程序替补。每个 seed 下，同色与交叉任务使用相同的对象列表和初始布局，只有任务文字及评估目标不同。

模型输入沿用 `src/planning.py` 的提示词，只包含任务、对象名和受限接口说明。场景 seed 和目标标签不进入模型输入；程序中的动作执行时由可信 worker 读取坐标。因此这里的多种子实验测量随机摆放下的集成表现，不能证明模型具有空间推理能力。场景 seed 也不控制远端模型的采样；`temperature=0` 不保证服务输出完全确定。

任务和 seed 在运行前固定，仍属于已有开发任务，seed=0 已参与过调试；不能将这批结果描述为全新的、无偏的泛化测试。报告只覆盖本清单，五个 seed 不足以代表复杂环境或论文基准。

## 使用

从项目根目录运行，环境准备和密钥配置与 `docs/planning.md` 相同。模型地址/名称覆盖顺序为 CLI、环境变量、配置文件；不会自动切换模型。输出默认使用唯一目录，也可用 `--output` 指定尚不存在的目录。

```powershell
# 无模型调用、无仿真：预览离线评估清单及冻结后的输入。
.\run_python.cmd run_evaluation.py --file-replay --execute --dry-run

# 离线编译全部参考程序；不会产生任务成功率。
.\run_python.cmd run_evaluation.py --file-replay

# 固定清单的真实生成与物理执行：默认 15 次模型请求。
.\run_python.cmd run_evaluation.py --model-api --execute

# 文件回放物理评估，用于区分模型问题和动作执行问题。
.\run_python.cmd run_evaluation.py --file-replay --execute
```

`--dry-run` 只保存新清单，不执行请求和仿真；生成的目录保留为预览，正式运行使用新目录。省略 `--execute` 时仍可请求模型，但仅校验程序，`task_success_rate` 始终为 `null`。

新增任务或 seed 时创建新版本的清单，不修改正在运行的协议。清单中的 `scene` 与 `program_file` 路径相对于清单文件解析。每个场景必须预先给出非空独立目标；参考程序只用于 `--file-replay`，模型模式绝不读取它作为模型回答。

网络参数默认 `temperature=0`、`thinking=auto`、输出预算 4096 tokens、socket 超时 120 秒；物理 worker 默认最多 48000 步、墙钟上限 180 秒。`--trial-timeout` 默认 420 秒，限制单个试验的总时长，超时终止本次进程树并保留已有产物。所有限额均保存到清单。

## 冻结与记录

每批输出包含：

- `manifest.json`：任务与 seed、独立目标、模型配置、限额、上游来源文件的哈希、Git 提交、实际执行代码哈希、每项提示词哈希。Git 提交可能早于工作区实现，以文件哈希为准。
- `inputs/`：场景和离线参考程序快照；原始场景之后变化不影响本次输入。
- `001_single_seed0/` 等目录：`run_planner.py` 的完整原始产物，包括失败回复。
- 每个试验对应的 `.log`：启动器输出；仿真日志在试验目录内部。
- `summary.json`、`trials.csv`、`summary.md`：逐次更新的结构化结果、逐试验表格与简表。

执行前逐次核对代码和输入快照哈希。代码/快照变化、模型身份或提示词不一致时停止后续试验。鉴权、服务调用和启动器等基础设施失败也停止批次，剩余试验标记为 `not_run`，不继续重复调用。正常的程序拒绝、物理失败和目标失败保留并继续后续试验。

不存在自动续跑或失败重试。需要新实验时使用新目录，保留旧批次及其停止原因；不得把多批挑选出来的成功记录合并成一次固定评估。

## 如何读结果

| 状态 | 含义 |
| --- | --- |
| `success` | 程序通过、物理执行通过、独立目标通过、worker 正常退出且必需产物存在 |
| `plan_rejected` | 回复无法转换为受限动作；没有启动仿真 |
| `physical_failure` | 抓放或最终动作关系没有满足既有判据 |
| `task_failure` | 执行动作成功，但独立任务目标不满足 |
| `api_failure` / `configuration_failure` | 服务调用或配置失败；停止后续试验 |
| `simulation_timeout` / `trial_timeout` | worker 或整个试验超时；保留部分产物 |
| `execution_error` / `runner_failure` | 仿真异常或启动/报告异常 |
| `protocol_mismatch` / `artifact_failure` | 协议与记录不一致或必需产物缺失，不计为成功 |
| `validated_only` | 仅程序校验，未验证任务成功 |
| `not_run` / `running` / `interrupted` | 尚未完成，不能作为已测任务 |

完整物理批次的成功率为 `success` 数量除以全部预设试验数，语法失败及物理失败均在分母中。未完成整批时总体成功率为 `null`；已完整结束的单个任务组仍可显示该组的结果。`task_success` 与 `execution_success` 分别保存，不能只看生成程序或单个动作是否通过。

API 用量仅累加服务实际返回的字段；缺失用量单独计数。超时等情况可能没有留下 API 请求标记，`trials_without_api_attempt_metadata` 会记录此类试验；`api_requests_attempted` 仅代表已确认次数，不能把未知调用成本当作零。

成功条件沿用当前系统的官方 `on_top_of` 与最大抬升超过 0.05 米；没有修改控制参数或放宽判据。批次完成后还需核对轨迹有限值、视频帧数、画面，以及 seed=0 与既有基线的对应关系。自动汇总只检查必需产物存在且非空，不代替这些内容核验。

## 与论文复现的关系

论文桌面仿真评估覆盖 8 类长程任务、6 类空间几何任务，并区分已见/未见指令和属性，每项任务进行 50 次试验。还比较 CLIPort 和自然语言规划器。当前清单只测量三类已实现的抓放任务，不可与论文表格直接比较。来源：[论文第 IV-D 节及附录 K](https://arxiv.org/html/2209.07753v4)。
